# TypeBreak

An adaptive typing tutor with two front ends — a terminal app and a web app —
sharing one lesson library, one scoring engine and one adaptive planner.

The idea is a personal typing coach: instead of a fixed curriculum, TypeBreak
measures how each finger performs and builds each day's practice from a
predefined library of drills, weighted toward whatever is costing you accuracy.

---

## Quick start

Node 22.18+ (uses ES modules and `node --test`). No dependencies, no build step,
no install.

```bash
npm start                 # interactive terminal app
npm run web               # web app at http://localhost:4173
npm test                  # 176 tests
```

Other useful commands:

```bash
node src/cli/index.js plan            # today's plan, non-interactive
node src/cli/index.js practise L-LRING-UP
node src/cli/index.js fingers         # per-finger progress
node src/cli/index.js why L-LRING-UP  # explain a recommendation
node src/cli/index.js --help
```

## Architecture

The whole point of the design is that **neither interface contains learning
logic**. Both call the same `AppService`, which is the only surface that knows
about lessons, scoring and persistence.

```
                      ┌──────────────────────┐
   CLI (src/cli)  ───▶│                      │
                      │     AppService       │───▶  data/state.json
   Web (src/server +  │  src/core/service.js │
        web/)     ───▶│                      │───▶  data/lessons.json
                      └──────────┬───────────┘       (read-only)
                                 │
        ┌────────────────┬───────┴────────┬─────────────────┐
        ▼                ▼                ▼                 ▼
   library.js       engine.js         profiles.js         bts.js
  (predefined      (typing session,  (finger/movement   (weakness detection,
   lessons,         metrics, error     rollups, streak,   lesson scoring,
   validation)      attribution)       history)           daily planner)
```

| Module | Responsibility |
| --- | --- |
| `src/core/keyboard.js` | Every key → finger → movement mapping. No state, no randomness. |
| `src/core/library.js` | Loads, validates and freezes the preset lesson library. Query only — no mutation API. |
| `src/core/engine.js` | `TypingSession`: consumes keystrokes, attributes errors to fingers, computes metrics. |
| `src/core/store.js` | Atomic JSON persistence with backup and crash recovery. |
| `src/core/profiles.js` | Derives finger/movement proficiency, streaks and history from attempts. |
| `src/core/bts.js` | The BTS algorithm: evaluate → identify → score → plan → explain. |
| `src/core/service.js` | The shared application surface used by both front ends. |
| `src/cli/` | Terminal UI: menus, raw-keystroke drill, progress screens. |
| `src/server/` | `node:http` server; a thin JSON wrapper over `AppService`. |
| `web/` | Dependency-free browser app: hash router, small DOM helpers, pages. |

### Why the split matters

- **The lesson library is fixed.** `data/lessons.json` is generated once by
  `tools/build-lessons.js` (deterministic, seeded). At runtime the library is
  loaded, validated and deep-frozen. There is no code path that adds a lesson or
  edits exercise text.
- **The planner can only select.** `planDay()` returns lesson *ids*. The
  library's validation and the `assertPlanUsesLibraryOnly` guard make it
  impossible for a plan to reference anything that did not come from the file.
- **Scoring lives in one place.** The browser forwards each keystroke to the
  server; the server scores it with the same `TypingSession` the CLI uses, and
  sends back the per-character states. Neither front end can disagree with the
  other because neither computes anything.

## The lesson library

Generated by `npm run lessons:build` into `data/lessons.json`:

```
55 lessons · 177 exercises
  finger-isolation     8
  movement-variation  29
  finger-combination   6
  pattern             11
  coordination         1
```

Coverage is validated at build time and asserted in tests:

- **All ten fingers**, including both thumbs (space-bar control).
- **All 16 movement variations**: home, up, down, number-row stretch,
  inner-column and outer-column reaches, thumb space, cross-hand alternation,
  same-hand rolls, index crossover, shift reach, digraphs, trigraphs, double
  letters, common words, and full coordination.

Each lesson carries: id, name, description, category, level (1–10), target
fingers, target movements, keys, exercises, learning outcome, related lessons,
performance criteria (accuracy gate; speed advisory), and an estimated duration.

Drills are generated with a seeded PRNG and weighted toward the target finger,
then frozen into JSON. Regenerating produces byte-identical output.

## BTS — Behavioural Typing System

`src/core/bts.js` is pure and deterministic: same state + same date ⇒ same plan.

### 1. Evaluate

Per finger and per movement, from accumulated character tallies:

```
severity = (accuracy gap / target) × 85  +  error volume × 15
```

Severity is deliberately continuous — a hard cap would make every bad finger
score 100 and hide which is worst. A finger at or above target has severity 0.

### 2. Identify

Findings require **multiple attempts and enough characters** before anything is
called a weakness. One bad run can never produce one; this is explicitly tested.
Findings cover weak fingers, weak movements, regressions (recent worse than
earlier), and lessons that take unusually long.

### 3. Score

Every lesson is scored on independent, individually-explainable signals:

| Signal | Fires when |
| --- | --- |
| `weakness` | The lesson targets a currently weak finger |
| `movement-weakness` | It trains a weak movement variation |
| `low-accuracy` | Your last attempt at it was below target |
| `new-material` | Untried, at or near your demonstrated level |
| `level-fit` | It matches the level you've shown you can handle |
| `stale` | Not practised for 7+ days |
| `not-passed` | Started but criteria not yet met |
| `regression` | A finger it trains has regressed |
| `difficulty-penalty` | Well above your demonstrated level |
| `mastered` | Passed with margin (suppressed if a target finger is now weak) |

Each signal appends a plain-English reason, so a recommendation can always be
traced to the numbers behind it.

### 4. Plan

Quotas, not a pure top-N — that is what keeps weakness work from crowding
everything out:

```
6 items = 3 weakness + 2 progression + 1 maintenance
```

Weakness slots are filled round-robin across weak fingers (worst first) so one
bad finger cannot take every slot, and each finger's group prefers lessons that
drill it *specifically* over broad lessons that happen to include it. Weakness
work is capped at 60% of the final plan; when a library genuinely lacks
non-weakness material the plan says so via `balance.status` rather than
mislabeling drills.

Plans are generated once per calendar day and reused, so the list does not
reshuffle mid-session. `--regen` / "Regenerate plan" forces a rebuild.

### 5. Explain

Every plan item and recommendation carries its reasons, and `plan.explanation`
is a readable paragraph naming the weaknesses the plan actually addresses (not
merely the worst ones on file).

## Typing engine

- **WPM** uses the conventional 5-characters-per-word definition and counts only
  characters typed correctly, so mashing keys cannot inflate it. Sub-second
  attempts are floored to avoid absurd rates.
- **Accuracy** is measured over *keystrokes*, so corrections cost accuracy the
  way they should.
- **Strict mode** holds the caret on a mistake — best for learning a new
  movement. **Flow mode** advances and records — best for measuring speed.
- **Error attribution**: every mistake is recorded against the expected
  character, and therefore against that character's finger and movement. This is
  what makes finger-level weakness detection possible.
- Timing is injected, so tests are deterministic and clock-free.

## Progress

All derived from attempts, never from completion counts:

- **Finger proficiency** = accuracy weighted by evidence (`min(1, chars/150)`),
  so a finger drilled ten times is not "mastered" on the strength of those keys.
- **Lesson passed** requires meeting the accuracy gate *and* finishing — speed
  alone cannot pass a lesson.
- **Overall progress** = 60% of share-of-lessons-passed + 40% of mean finger
  accuracy. Completing lessons without accuracy cannot reach 100%.
- Streaks, 30-day history, movement proficiency and per-lesson stars are all
  computed the same way for both interfaces.

## Data

One file, `data/state.json`, shared by both front ends:

```
profile.settings
attempts[]        every recorded attempt with metrics and attributed errors
plans{}           generated daily plans, keyed by date
tasks{}, assessments{}
```

- Writes are atomic (temp file → rename) with the previous document kept as
  `.bak`.
- A corrupt primary file is recovered from the backup; if both are unreadable
  the damaged file is quarantined rather than silently overwritten.
- `migrate()` upgrades older documents additively and drops records that cannot
  be interpreted, instead of failing the whole load.

Practise in the terminal, then refresh the browser — it reads the same file.

## Adding lessons

1. Edit `tools/build-lessons.js` (add a finger/movement combination or a skill
   lesson).
2. Run `npm run lessons:build`.
3. Run `npm test` — coverage, id-uniqueness and mappability are all asserted.

No change to the BTS algorithm, the engine, or either interface is required.
That is the point of separating the library from the planner.
